# 인터넷 구조와 웹 열람 구조

> [!summary] 이번 회차 한줄 요약 인터넷의 기원과 라우터의 역할 → 그 위에서 동작하는 서비스 프로토콜(메일) → 웹이 실제로 화면에 뜨기까지 거치는 구조(URL/HTTP/DNS/ICMP) 순으로, "인터넷이 실제로 어떻게 굴러가는가"를 다룹니다.

## 21. 인터넷 구조

### 21-1. 기원

- 1967년 시작된 ARPANET 계획의 패킷통신망 연구에서 기원
- 1969년 ARPANET 가동, 미국 대학 4곳 + 연구 기관 연결
- 이 연구 성과 중 하나로 TCP/IP 프로토콜 개발
- "internet"이라는 용어는 1974년 무렵부터 쓰이기 시작했고, 1983년 ARPANET이 TCP/IP로 전면 전환하면서 고유명사로 자리잡음. 지금처럼 대중적으로 쓰인 건 1990년대 WWW 등장 이후
- 네트워크끼리 대등한 관계로 서로 연결되어 있다는 의미에서 "inter-net(망 사이)"이라는 이름이 붙음

### 21-2. 인터넷을 구성하는 핵심 장치 — 라우터

라우터는 네트워크를 연결하고 패킷의 교통정리를 수행하는 장치. 전 세계 LAN, ISP, 모바일 네트워크를 서로 이어주는 역할을 함.

**라우터 기본 기능**

|기능|내용|
|---|---|
|내부 통신 차단|LAN 내부의 통신은 외부로 내보내지 않는다|
|외부 통신 필터링|자신의 LAN 주소가 아닌 통신은 내부로 들여보내지 않는다|
|경로 결정|자신의 LAN 주소가 아닌 통신은 라우팅 테이블이나 기본 게이트웨이를 통해 전달한다|

> [!note] 핵심 이 세 가지가 가능한 이유는 라우터가 IP 주소를 "자기 자신/자신이 관리하는 LAN/전송 대상"을 구분하는 식별자로 쓰기 때문. 결국 라우터의 모든 판단 기준은 IP 주소임.

### 21-3. 인터넷에서 사용하는 프로토콜

인터넷의 기본 프로토콜은 TCP/IP이지만, 이메일 송수신이나 웹 열람처럼 실제로 우리가 쓰는 서비스는 TCP/IP만으로는 구현되지 않는다. TCP/IP 기반 위에 다양한 상위(서비스) 프로토콜이 얹혀야 비로소 서비스가 됨.

**왜 TCP와 IP를 나눠서 봐야 하는가**

|계층|역할|
|---|---|
|IP|주소를 기반으로 패킷을 전달하는 역할만 담당. 도착 확인이나 재전송은 하지 않음 (best-effort)|
|TCP|세션을 맺고(3-way handshake), 순서를 보장하고, 누락된 데이터를 재전송하는 역할까지 책임짐|

> [!note] 핵심 재전송을 애플리케이션이 직접 신경 써야 하는 경우는 TCP 대신 UDP를 쓸 때뿐이다. TCP를 쓰는 순간 "도착했는지, 재전송이 필요한지"는 전부 TCP가 알아서 처리하고, 애플리케이션은 신경 쓸 필요가 없다.

**서비스 프로토콜**

- IP, TCP/UDP를 기반으로 상위 기능을 구현한 것 (SMTP, HTTP, FTP 등)
- 잘 알려진 포트 번호(22, 80, 443, 3389 등)는 대부분 이런 서비스 프로토콜에 대응됨 → 포트 번호만 봐도 "이 트래픽이 무슨 서비스인지" 짐작 가능

### 21-4. 이메일을 주고받는 구조 (SMTP/POP/IMAP)

메일을 보내는 프로토콜(SMTP)과 받는 프로토콜(POP/IMAP)이 분리되어 있다는 게 핵심.

**SMTP — 어떻게 상대방 메일 서버를 찾는가**

`user@example.com`으로 메일을 보낼 때, 발신 SMTP 서버는 "example.com의 웹서버"가 아니라 "example.com의 **메일 서버**"를 찾아야 함. 이 둘은 완전히 다른 서버일 수 있기 때문에, DNS에서 일반 A 레코드가 아니라 **MX 레코드(Mail eXchange record)**라는 메일 전용 레코드를 조회해서 메일 서버 주소를 얻음.

**POP vs IMAP**

| 구분   | 방식                        | 특징                                             |
| ---- | ------------------------- | ---------------------------------------------- |
| POP  | 클라이언트가 인증 후 이메일을 로컬로 다운로드 | 다운로드하면 서버 스풀 파일에서 삭제됨 → 같은 계정이라도 다른 기기에서 확인 불가 |
| IMAP | 서버에서 이메일을 계속 관리           | 스풀 파일에서 삭제되지 않음 → 같은 계정이면 모든 기기에서 동기화되어 확인 가능  |

> [!note] 핵심 POP는 "다운로드해서 소유", IMAP은 "서버를 계속 들여다봄"이라는 방식 차이가 멀티 디바이스 동기화 여부를 결정한다.

## 22. 웹페이지를 열람할 수 있는 구조

### 22-1. 웹의 인프라 기술

- 웹 = World Wide Web, 클라이언트-서버 모델
- 인프라 기술: TCP/IP, HTTP/HTTPS, DNS
- 구성 요소: 웹서버(Apache, IIS, NGINX 등), 웹클라이언트(브라우저), HTML/JavaScript/PHP/Java 등 언어, SQL 등 DB, XML, REST API
- 초기 웹은 학술 논문 등 정보를 열람하는 서비스로 출발했고, 문자·수식·그림뿐 아니라 향후 동영상/음성까지 통합 가능한 형식으로 **HTML**이 채택됨

### 22-2. URL/URI/URN — 포함 관계로 이해하기

세 용어가 나란히 있는 개념이 아니라, 포함 관계에 있음.

|용어|의미|관계|
|---|---|---|
|URI|리소스를 식별하는 방법 전체|가장 큰 개념|
|URL|**위치**로 리소스를 식별|URI의 부분집합 (우리가 흔히 쓰는 방식)|
|URN|**이름**으로 리소스를 식별 (위치 무관)|URI의 부분집합|

URL 구조에는 프로토콜(HTTP, HTTPS, FILE, DATA 등 예약어), 도메인 이름, 임의의 변수 값 등을 지정할 수 있음.

### 22-3. HTTP/HTTPS

- HTTPS = HTTP + 보안 강화(패킷 페이로드 암호화)
- 클라이언트-서버 모델: 브라우저가 요청(URI로 기술) → 서버가 해당 HTML 파일로 응답
- HTTP는 하위 프로토콜로 TCP를 써서 세션을 설정하지만, 요청/응답 자체는 전후 통신과 무관하게 매번 독립적으로 처리됨 → **스테이트리스(Stateless)**

> [!note] 왜 스테이트리스로 설계했는가 웹 서버는 불특정 다수의 브라우저 요청을 동시에 처리해야 하는데, 접속마다 상태를 계속 유지하면 서버 부담이 기하급수적으로 커짐. 그래서 매 요청을 독립적으로 처리하는 스테이트리스 방식을 택함. 대신 두 가지 보완 장치가 붙음.

|보완 장치|무엇을 해결하는가|
|---|---|
|캐시|같은 페이지를 반복 요청할 때마다 같은 HTML을 매번 새로 받는 낭비를 줄임 (업데이트 없으면 로컬 캐시 사용)|
|쿠키|로그인 유지처럼 "상태"가 필요한 경우, 클라이언트가 상태 정보(Set-Cookie)를 직접 들고 다니면서 스테이트리스의 한계를 우회|

### 22-4. DNS (Domain Name System)

IP 주소는 유일한 식별자이지만 숫자 나열이라 사람이 다루기 어려움. 그래서 사람이 다루기 쉬운 이름(도메인)과 IP 주소를 매핑해서 관리하는 체계가 DNS.

**조회는 계층적으로 이루어짐**

|단계|역할|
|---|---|
|루트 DNS 서버|최상위. ".com은 어디가 관리하는지" 등 TLD 서버 위치를 안내|
|TLD 서버|.com, .kr 같은 최상위 도메인 단위 관리, 하위 권한DNS서버 위치를 안내|
|권한DNS서버(네임서버)|실제 도메인-IP 대응표(영역, zone)를 갖고 최종 IP를 응답|

이 조회 과정을 클라이언트 쪽에서 대신 처리해주는 프로그램이 **리졸버**. DNS 서버에 포함되어 있기도 하고, 기기 쪽에서 문의만 처리하는 스텁 리졸버 형태로 존재하기도 함.

### 22-5. ICMP (Internet Control Message Protocol)

목적지와 연결을 맺기 전 정보를 교환하거나, 패킷이 잘 도착했는지 확인하는 등의 기능을 규정한 프로토콜. 오류 통지와 통신 상태 확인에 쓰이며, LAN을 넘어 인터넷 전체로도 전송됨.

TCP/UDP와 마찬가지로 ICMP 헤더+페이로드가 IP 패킷의 페이로드 안에 캡슐화되는 구조. 다만 포트 번호 대신 **타입(Type)/코드(Code)**로 목적을 구분한다는 점이 다름.

![[icmp_in_ip_encapsulation.svg]]

**자주 쓰이는 Type 값**

| Type | 이름                      | 용도                         |
| ---- | ----------------------- | -------------------------- |
| 8    | Echo Request            | ping 요청                    |
| 0    | Echo Reply              | ping 응답                    |
| 3    | Destination Unreachable | 목적지에 도달할 수 없음              |
| 11   | Time Exceeded           | TTL 만료 (traceroute의 핵심 원리) |

> [!tip] traceroute의 원리 IP 패킷의 TTL을 1부터 하나씩 늘려가며 전송하면, 각 홉의 라우터가 TTL 만료로 "Time Exceeded" ICMP 메시지를 되돌려줌. 이를 이용해 경로 전체를 추적하는 것이 traceroute.

> [!tip] ICMP와 보안 ICMP는 원래 상태 확인용이지만, 1990년대 후반 **Smurf 공격**(ICMP Echo를 브로드캐스트로 뿌려 DDoS 유발)처럼 악용된 사례 때문에 요즘은 방화벽에서 ICMP를 기본 차단하는 경우가 많음. 그래서 "핑은 안 되는데 서비스는 정상"인 상황이 실무에서 흔히 발생함.

> [!tip] HTTP의 진화 - QUIC HTTP/1.1까지는 TCP 기반이었지만, HTTP/3부터는 **QUIC**이라는 UDP 기반 프로토콜 위에서 동작함. TCP의 순서보장·혼잡제어로 인한 지연 문제를 UDP + 자체 로직으로 우회한 사례로, "TCP는 신뢰성, UDP는 속도"라는 이분법이 요즘은 조금씩 흐려지고 있음.
