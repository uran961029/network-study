## 15. 클라이언트 서버형과 피어 투 피어형

### 클라이언트-서버형

- 미니컴퓨터·워크스테이션이 보급되면서 함께 확산된 구조
- 한쪽(서버)이 애플리케이션/네트워크 서비스를 실행해서 제공하고, 다른 쪽(클라이언트)은 그 서비스를 요청·이용
- 명칭은 **장치 자체가 아니라 역할**에 붙는다
    - 메일을 제공하면 메일서버, 파일을 제공하면 파일서버
    - 메인프레임이나 워크스테이션이라도 다른 장치의 서비스를 받는 입장이면 그 순간엔 클라이언트

> [!tip] IoT 장치가 서버가 되는 경우 
>  [감시카메라 예시] 
>  감시카메라는 그냥 "찍기만 하는 장치"처럼 보이지만, 내부에 작은 웹서버(또는 RTSP 서버)가 들어있다. 카메라의 IP로 스마트폰 앱/브라우저가 접속하면 카메라가 영상을 "서비스"로 제공 → 카메라 = 서버, 보는 앱 = 클라이언트
>  
> 즉 "서버"가 꼭 큰 컴퓨터일 필요는 없고, 칩 하나에 서버 기능만 들어있어도 그 순간 서버 역할을 한다.


### 역할은 고정이 아니라 방향에 따라 정해진다

같은 컴포넌트라도 "누구한테 요청을 보내느냐"에 따라 역할이 바뀐다.
![[Pasted image 20260622000623.png]]

- 사용자(브라우저): 항상 요청만 보내는 입장 → 영원히 클라이언트
- 웹서버/로드밸런서: 사용자 입장에선 서버, 뒷단 WAS에 요청을 넘기는 순간 WAS 입장에선 클라이언트
- WAS: 웹서버에게는 서버, RDS·Object Storage에 쿼리/파일 요청을 보낼 때는 클라이언트
- RDS, Object Storage: 끝까지 요청을 받기만 하고 먼저 보내는 법이 없음 → 항상 서버

> [!note] 핵심
> DB나 스토리지처럼 "한쪽 끝"에 있는 컴포넌트는 역할이 절대 안 바뀐다. 나머지는 누구와 통신하느냐에 따라 서버도 됐다가 클라이언트도 된다.

> [!tip] 알아두면 편한 점
> 1. **Security Group 설계**: 서버 역할 쪽은 inbound를 열어야 함(요청을 받아야 하니까), 클라이언트 역할만 하는 쪽은 outbound만 있으면 됨. 
> 2. **장애 지점 파악**: "WAS→DB 접속 안 됨"이면 WAS는 클라이언트 입장이니 outbound 트래픽 + DB 쪽 inbound 룰을 같이 봐야 한다는 게 바로 나옴.
> 3. **아키텍처 다이어그램**: 박스만 나열하지 않고 화살표 방향(누가 누구에게 요청하는지)까지 표시하면 트래픽 흐름이 한눈에 들어옴.

##### ⁂ 서버를 거치는 구조의 한계

클라이언트-서버 구조는 모든 트래픽이 서버 한 곳을 지나가는데, 이게 세 가지 문제를 만든다.

- **비용/대역폭**: 화상통화 100명이 동시 접속하면 서버는 100명분의 업로드+다운로드를 다 떠안아야 함
- **레이턴시**: A→서버→B로 가면 A→B 직결보다 무조건 더 오래 걸림 (같은 동네 사람끼리 통화하는데 서버가 지구 반대편이면 체감 지연이 커짐)
- **단일 장애점(SPOF)**: 서버가 죽으면 전체가 마비됨

그래서 실시간성이 중요하거나 같은 LAN 안에 있는 등 "굳이 중간을 안 거쳐도 되는" 상황에서는 직접 연결이 합리적인 선택이 된다.
### 피어 투 피어형 (P2P)

- TCP/IP·인터넷도 원래는 전 세계 미니컴퓨터를 연결하려고 고안된 기술
- 인터넷의 기본은 클라이언트-서버형이지만, 실시간 동영상 전송이나 맞춤형 통신처럼 **서버를 거치지 않는 게 더 효율적인 경우**가 있음
- P2P: 인터넷에서 IP 주소 + 전용 통신 앱을 이용해 LAN의 단말끼리 직접 연결하는 방식

- P2P의 진짜 난제 — NAT 통과 문제

사설 IP는 외부에서 직접 들어올 수 없다(NAT/NAPT 챕터 참고). P2P로 연결하려는 두 단말이 둘 다 NAT(공유기) 뒤의 사설 IP라면, 서로의 공인 주소를 몰라서 직접 연결을 시작할 방법이 없다.

> [!note] 연결 수립 순서 — ICE 프레임워크
> 	ICE: 시그널링 서버, STUN, TURN을 어떤 순서로 조합해서 쓸지 정해놓은 표준절차(알고리즘, 방법론)로,  두 피어가 NAT나 방화벽 뒤에서도 서로 통신할 수 있도록 가능한 연결 경로를 찾는 절차를 의미함.
> 		실제로 하는일 
> 			1. Candidate 수집(Gathering): 내가 연결될 수 있는 모든 주소 후보 모으기
> 			2. Candidate 교환: 모은 후보 목록을 시그널링 서버를 통해 상대방한테 전달
> 			3. 연결성 검사: 받은 후보들과 내 후보들을 짝지어서, 우선순위 순서대로 하나씩 실제로 연결되는지 STUN 메시지로 핑퐁 테스트
> 
> 1. **시그널링 서버** (항상 필요): 두 피어가 서로의 존재 자체를 모르기 때문에, 연결 정보(SDP, ICE candidate)를 먼저 교환시켜주는 중개 서버. 보통 일반적인 웹서버/WebSocket 서버. ※ STUN과는 별개의 역할
> 2. **Host candidate (사설 IP)** 먼저 시도 — 같은 LAN이면 사설 IP끼리 바로 연결 성공, STUN까지 갈 필요 없음
> 3. 실패 시 **STUN**으로 알아낸 공인 IP:포트(Server-reflexive candidate)로 시도 — 서로 다른 네트워크의 NAT 뒤에 있는 피어끼리 통신할 때 등장
> 4. 그래도 실패(대칭형 NAT 등) 시 **TURN**이 데이터를 계속 중계 — 사실상 클라이언트-서버로 돌아간 것이라 P2P로 보기 애매함

#### 3. 실제 사례

|사례|방식|
|---|---|
|Zoom/Google Meet 같은 화상회의|가능하면 P2P, 안되면 TURN 서버 경유 (WebRTC 기반)|
|토렌트|순수 P2P에 가까움. 트래커/DHT로 피어 목록만 찾고 파일은 피어끼리 직접 주고받음|
|온라인 게임 (호스트 기반 로비)|플레이어 중 한 명이 임시 "호스트" 역할 — 클라이언트-서버와 P2P의 중간 형태|
|블록체인|모든 노드가 대등한 피어, 중앙 서버 자체가 없음|

## 16. LAN

### LAN을 구성하는 장치와 프로토콜

- 트위스트 페어 케이블(LAN 케이블) + RJ-45 커넥터로 장치 연결
- 식별자는 기본적으로 MAC 주소지만, 실제로는 상위 계층(TCP/IP)의 IP 주소도 함께 사용

> [!note] 왜 MAC 주소만으로는 부족하고 L3 스위치가 필요한가
> 
> - MAC 주소는 제조사 식별 정도만 있고, **계층 구조가 없는 평면적(flat) 주소**다 → "이 장치가 어느 부서/어느 층인지"와 무관
> - IP 주소는 네트워크부 + 호스트부로 나뉘어 **서브넷 단위로 계층적 관리**가 가능 (영업부 대역, 개발팀 대역 식으로)
> - L2 스위치는 MAC만 보기 때문에 조직이 커지면 관리가 번거로워짐
> - 그래서 IP(서브넷) 기준으로 라우팅/관리할 수 있는 **L3 스위치**를 도입해 부서별로 깔끔하게 나눔
> - 정리: 스위치는 원래 L2 장치(MAC만 식별)지만, L3 스위치는 IP 주소도 식별자로 쓸 수 있는 스위치

### 구체적인 LAN의 실체

1. 컴퓨터·서버는 LAN 케이블로 스위치와 연결 → 스위치 하나가 LAN의 최소 단위
2. L3 스위치/라우터로 여러 스위치를 묶어서 과·부·사업소 등 조직 구성에 맞춤
3. **L2 스위치로 묶인 LAN끼리는 그 자체로 통신 불가** → 해결책 두 가지
    - 스위치를 캐스케이드(다단) 연결
    - 모든 장치를 연결할 수 있는 대형 스위치 사용
4. 사무실 전체를 하나의 LAN으로 묶지 않는 이유: 유지보수 번거로움 + 보안 문제 → L2 스위치 묶음 사이를 정리해주는 **라우터(또는 L3 스위치)** 도입

> [!tip] 캐스케이드 연결, 몇 대까지 가능한가
> 
> - **허브(리피터) 시절**: 10BASE-T 기준 "5-4-3 규칙" — 세그먼트 5개, 리피터 4대, 단말 연결 가능한 세그먼트 3개까지. CSMA/CD 충돌 감지 타이밍 때문에 생긴 진짜 고정 숫자 제한이었음
> - **스위치 시절**: 충돌 도메인 자체가 없어서 IEEE 표준상 정해진 고정 숫자는 없음. 대신 너무 깊게 캐스케이드하면 **브로드캐스트 스톰**, STP 컨버전스 지연 같은 문제가 생겨서 실무적으로 깊이를 제한 권고
> - 한 줄 요약: 옛날 허브는 물리적 제약으로 숫자가 못박혀 있었고, 스위치는 숫자 규격은 없지만 성능상의 이유로 깊게 안 가는 게 좋다

## 17. 무선LAN

### 장단점

|장점|단점|
|---|---|
|케이블 제약 없이 전파가 닿는 범위에서 자유롭게 설치|전파를 누군가 무단으로 가로챌 수 있음|

### 보안 대책과 한계

|대책|방식|한계|
|---|---|---|
|MAC 주소 인증|허용된 MAC만 연결 허용|주소 테이블을 조사하는 방식으로 우회 가능|
|SSID 식별|액세스 포인트 식별용 SSID 사용|기본은 브로드캐스트됨|
|스텔스 SSID|SSID 브로드캐스트 제한|프로토콜을 알면 SSID를 요청해서 알아낼 수 있음|
|암호화|통신 자체를 암호화|방식에 따라 안전도 차이 큼 (아래 참고)|

> [!note] 이 셋 다 프로토콜 자체에 구현돼 있지만, 완전한 보안은 아니다. 그래서 LAN 내 별도 인증 서버를 두는 등 **상위 계층의 보완**이 필수.

### 암호화 방식 비교

- **WEP**: RC4 알고리즘 기반. 현재 컴퓨터 성능이면 몇 시간 안에 분석 가능 + 분석 도구도 흔함 → 사용 비권장
- **WPA**: TKIP로 암호화를 복잡화. 이후 **WPA2 → WPA3**로 계속 개량
- 결론: 무선 LAN을 안전하게 쓰려면 WPA 계열(WPA2/3) 필수 + 가능하면 인증 서버 연동

## 18. WAN

### 정의

- Wide Area Network — 건물 내부/외부처럼 LAN보다 넓은 범위를 연결
- 용어로서는 "불특정 다수의 호스트/디바이스가 연결되는 네트워크(망)" 자체를 가리키기도 함
- KT·SKT 같은 통신사업자가 제공하는 전용선도 WAN의 한 형태
    - 전용선 = 계약자가 회선을 독점 (은행 ATM 회선처럼). 특정 거점-데이터센터 연결이나 IX 연결 등에 사용

### LAN과 WAN의 관계가 변해온 방식

1. 과거엔 단순히 "연결 범위의 차이"를 나타내는 용어였음
2. 그런데 **광역 LAN**이라는 서비스도 있음 — 이더넷을 그대로 쓰면서 중간에 게이트웨이/다른 프로토콜을 끼워 원거리 거점을 연결 → 네트워크 종류 자체는 LAN
3. 기업 LAN 내부에서도 WAN이라는 용어가 쓰임 — 라우터 포트에 LAN/WAN이 같이 표시되는 경우
    - 여러 세그먼트를 모으는(집선하는) 쪽 = LAN
    - 다른 라우터/상위 라우터로 나가는 쪽 = WAN
    - 여기서 WAN은 "LAN의 바깥"을 의미

> [!note] 결론 LAN과 WAN의 차이는 절대적인 거리 기준이 아니라, **"로컬"이 가리키는 범위의 안쪽이냐 바깥쪽이냐**의 상대적 차이.

>[!note] 참고: PAN / MAN도 있다
>- PAN(Personal Area Network): 블루투스 이어폰, USB 연결처럼 개인 기기 간 초근거리 네트워크
>- MAN(Metropolitan Area Network): 도시 단위 규모. 캠퍼스나 지자체망, ISP 백본 정도에서나 쓰이고 SA가 직접 설계할 일은 거의 없음
>- 실무에서는 이 전체 스펙트럼보다 **LAN/WAN 이분법**으로 사고하는 게 훨씬 실용적

> [!tip] 클라우드에서 Direct Connect/전용회선이 전형적인 WAN 사례. VPC 내부는 LAN 개념에 가깝고, 그 경계 바깥(인터넷, 다른 리전, 온프레미스 연결 구간)은 WAN 개념과 비슷하게 적용된다 — 즉 클라우드에서도 "내 VPC 기준 안/바깥"이라는 상대적 관점이 그대로 통한다.

## 19. VLAN

### 기본 개념

- LAN의 최소 단위 = 스위치 하나로 묶인 세그먼트 (같은 스위치에 연결된 장치들이 한 세그먼트)
- 일반적인 기업 LAN: 관리 편의를 위해 층별/부서별로 세그먼트 분리, 스위치도 그에 맞춰 준비
- 문제: 스위치에 연결 가능한 장치 수는 한정 → 장치가 늘면 새 세그먼트 추가 필요
- **VLAN**을 쓰면 **서로 다른 물리적 스위치에 연결된 장치도 같은 논리적 세그먼트로 묶을 수 있음**

### 세그먼트를 나누는 이유

- VLAN-ID라는 식별자로 스위치 안팎의 논리적 세그먼트를 구성
- "같은 세그먼트" = 2계층에서 브로드캐스트 패킷이 도달하는 범위
    - ARP, DHCP 같은 프로토콜은 목적지를 찾거나 IP를 요청할 때 **네트워크 전체에 브로드캐스트** 전송을 함
- 세그먼트를 잘 관리하지 않으면 → 관련 없는 세그먼트까지 불필요한 브로드캐스트 패킷이 흩어짐
- 3계층(라우터)은 IP 주소 + 서브넷으로 세그먼트를 관리
- VLAN 기능은 L3 스위치뿐 아니라 **L2 스위치도 지원**하는 경우가 많음

> [!tip] 클라우드 관점 — VPC/Subnet = VLAN의 클라우드 버전 NHN Cloud·AWS의 **VPC + Subnet 구조**가 사실상 VLAN의 클라우드식 구현이다.
> 
> - 물리 스위치 제약 없이 논리적으로 네트워크를 나눈다는 점이 VLAN과 동일한 발상
> - 여기에 **Security Group**이 추가 레이어로 트래픽을 한 번 더 통제 (VLAN에는 없던 개념)
> - 즉 "온프레미스에서 VLAN으로 하던 일"을 클라우드에서는 VPC/Subnet 설계로 하는 셈

## 20. SDN

### VLAN/태그 기반 가상화의 한계

- VLAN처럼 논리적 구성으로 네트워크를 관리하는 기술을 **가상 네트워크**라고 부름
- VLAN 외에도 **VPN**, **MPLS**(Multi-Protocol Label Switching) 등이 있음
- 공통점: 태그/레이블을 이용해 네트워크 설계·구성을 가상화 → 배선이나 장치 배치 제약 없이 구성 가능
- 한계: 그래도 스위치·라우터를 **개별적으로 설정**해야 함
- 더 대규모/유연한 네트워크가 필요하면 태그·레이블 가상화만으로는 부족 → **SDN**으로 대응

> [!note] MPLS란? 패킷에 전용 태그(레이블) 정보를 붙여서 라우팅을 제어하는 기술. VLAN-ID와 비슷하게 "레이블 기반으로 경로를 정한다"는 발상.

### SDN의 핵심: 관리·제어 기능의 집약

1. 전용 스위치로 각 장치를 하나의 LAN으로 모음
2. **데이터 플레인**(장치를 연결하는 하드웨어 기능)과 **컨트롤 플레인**(라우팅을 관리·제어하는 소프트웨어 기능)을 분리
3. 설정 정보와 네트워크 제어를 컨트롤 플레인에 집중 → 상세 구성/제어는 여기서 한 번에 처리

### 관리·제어 방식

- **REST API**: 웹 애플리케이션/서비스를 호출하는 표준 규약. 웹 브라우저로 다양한 서비스를 이용하듯, SDN의 데이터 플레인 제어나 컨트롤 플레인 설정도 REST API(또는 웹 브라우저)로 가능
- 표준 프로토콜: **NETCONF**, **OpenFlow**

> [!tip] 클라우드 관점 — 사실 VPC 자체가 SDN으로 돌아간다 NHN Cloud나 AWS에서 VPC를 콘솔 클릭 몇 번, 또는 Terraform 코드 한 줄로 만들 수 있는 이유가 바로 SDN이다.
> 
> - 사용자(SA)가 보는 건 **REST API**(콘솔/CLI/Terraform)뿐
> - 실제 물리 네트워크 장비 제어는 클라우드 사업자의 **SDN 컨트롤러**가 뒤에서 처리
> - 즉 VLAN이 "논리적 분리"의 시작이었다면, SDN은 그 분리·관리를 API 한 번으로 완전히 추상화한 결과물 — VPC가 바로 그 결과물
