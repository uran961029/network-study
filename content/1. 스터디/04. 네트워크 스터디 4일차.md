
## DHCP (Dynamic Host Configuration Protocol)

LAN 내 장치에 IP 주소를 자동으로 할당하는 프로토콜.

> [!note] DHCP 서버는 누가 담당하나? DHCP 서버 역할은 별도 서버 장비가 담당하는 게 원칙이지만, 가정/소규모 환경에서는 **라우터 장비 안에 DHCP 서버 프로그램이 내장**되어 있어 라우터가 두 역할을 겸한다. 기업 환경에서는 별도 서버(Linux/Windows Server)를 두는 경우가 많다.

### DHCP가 필요한 이유

- LAN 내부 장치에는 프라이빗 IP 주소를 할당해야 함
- 수동 설정은 비효율적이고 실수가 잦음
- DHCP를 이용해 자동으로 할당

### 클라이언트-서버형 프로토콜

> [!tip] 클라이언트-서버형이란? 역할이 둘로 나뉘는 구조를 말한다.
> 
> - **서버**: 특정 처리를 전문으로 하는 쪽 (IP를 할당해주는 쪽)
> - **클라이언트**: 서버에 접근해서 서비스를 이용하는 쪽 (IP를 요청하는 쪽)
> 
> DHCP는 요청(클라이언트)과 응답(서버)이 명확히 나뉘기 때문에 클라이언트-서버형 프로토콜이라고 부른다.

### DHCP 서버 (IP를 할당해주는 쪽)

- 라우터, 고기능 스위치, Linux/Windows 서버 안에서 프로그램으로 동작

### DHCP 클라이언트(IP를 요청하는 쪽)

- Windows, macOS, Linux, Android, iOS 등 주요 OS 기본 탑재

### IP 주소 자동 할당 절차: D.O.R.A

```
1. Discover  — 클라이언트가 브로드캐스트로 DHCP 서버를 탐색
2. Offer     — DHCP 서버가 사용 가능한 IP 주소를 제안
3. Request   — 클라이언트가 제안된 IP 주소를 사용하겠다고 요청
4. Ack       — DHCP 서버가 최종 승인, IP 할당 완료
```

> [!note] Request가 브로드캐스트인 이유 DHCP 서버가 여러 대일 경우, 선택받지 못한 서버들도 동시에 통보를 받아 자신의 Offer를 철회할 수 있도록 하기 위해서다. Offer는 유니캐스트로 받았어도, Request는 브로드캐스트로 보내서 "나는 A 서버 거 쓰기로 했다"는 사실을 모든 서버에게 알린다.

### 임대(Lease) 개념

- DHCP는 IP를 **영구 소유가 아니라 임대** 방식으로 줌
- 갱신 시 Discover 없이 **Request → Ack** 2단계만 진행 (서버 위치와 IP가 이미 정해져 있으므로)

> [!note] 갱신 타이밍 만료 직전에 갱신하면 응답이 오는 사이에 IP가 끊길 수 있어, 미리 여유를 두고 갱신한다.
> 
> - 임대 기간 **50%** 시점 → 첫 갱신 시도 (Request)
> - 임대 기간 **87.5%** 시점 → 실패했으면 재시도
> - 만료 직전 → 그것도 실패하면 Discover부터 다시 (DORA 전체)

|환경|임대 기간|이유|
|---|---|---|
|카페 Wi-Fi 등|짧게 설정|접속자 회전율이 높아 IP 풀 재활용 필요|
|기업 네트워크|8~24시간|안정적 운영|
|클라우드|수백~수천 시간|인스턴스가 오래 떠있는 환경|

### DHCP 서버 이중화

- 기업 환경에서는 DHCP 서버가 단일 장애점이 되지 않도록 이중화
- 메인 서버 다운 시 백업 서버가 갱신 요청 처리
- 클라우드는 플랫폼 레벨에서 자동 이중화

> [!note] DHCP 서버가 전부 죽으면?
> 
> - **기존에 IP를 받은 장치** → 임대 기간 동안은 그대로 사용 가능
> - **신규 연결 시도** → Discover 날려도 응답 없음 → IP 못 받음 → 연결 불가
> - **갱신 시점이 온 장치** → 갱신 못 함 → 임대 만료 시 IP 잃음
> 
> 시간이 지날수록 하나씩 IP를 잃어가는 구조.

### DHCP Relay Agent

브로드캐스트는 라우터를 넘지 못하기 때문에, 다른 서브넷의 DHCP 서버에 요청하려면 **DHCP Relay Agent**가 필요하다.

라우터가 브로드캐스트를 유니캐스트로 변환해서 대신 전달.

### 클라우드에서의 DHCP

- 서브넷 생성 시 DHCP 자동 활성화 (별도 설정 불필요)
- DHCP 프로토콜을 사용하되 **항상 같은 IP를 할당** (MAC 주소 기반 고정)
- DHCP가 관여하는 것은 **사설 IP**만 해당 (공인 IP는 별도로 Floating IP 할당)

**NHN Cloud 서브넷 예약 IP (192.168.0.0/24 기준)**

|IP|용도|
|---|---|
|192.168.0.0|네트워크 주소|
|192.168.0.1|게이트웨이 주소|
|192.168.0.2|DHCP 서버 또는 SNAT용 IP|
|192.168.0.3|DHCP 서버 또는 SNAT용 IP|
|192.168.0.255|브로드캐스트 주소|

> [!note] .2/.3의 역할이 "또는"인 이유 
> 
> IGW 연결 여부에 따라 역할이 달라진다.
> 
> - IGW 없는 서브넷 → .2, .3 모두 DHCP 서버 (이중화)
> - IGW 있는 서브넷 → .2는 DHCP 서버, .3은 SNAT용 IP
> 
> IGW를 붙이는 순간 .3을 SNAT용으로 가져다 쓴다. 단, IGW 연결 타이밍에 따라 .3이 이미 사용 중이면 다른 IP가 SNAT용으로 쓰일 수 있어서 "또는"으로 표현한 것.

**AWS vs NHN Cloud IP 유지 차이**

|상황|AWS|NHN Cloud|
|---|---|---|
|재부팅|사설 IP 유지|사설 IP 유지|
|중지 후 시작|사설 IP 바뀜|사설 IP 유지|
|공인 IP 고정|Elastic IP 별도 부착|Floating IP 별도 부착|

> [!note] AWS에서 중지 후 시작 시 IP가 바뀌는 이유 
> 인스턴스를 완전히 끄면 AWS가 그 가상머신을 다른 물리 서버로 옮겨버릴 수 있다. 
> 물리 서버가 바뀌면 MAC 주소 기반으로 IP를 추적하기 어려워져 새로 DHCP 할당을 받게 된다. 
> NHN Cloud는 중지 후 시작해도 같은 IP를 유지하도록 플랫폼 레벨에서 보장한다. AWS에서 IP를 고정하려면 Elastic IP를 따로 붙여야 하는 이유가 이것.

## NAT와 NAPT

LAN 내부의 프라이빗 IP 주소는 인터넷에서 직접 사용할 수 없다. 인터넷에 접속하려면 **NAT 또는 NAPT**를 사용해 IP 주소를 변환해야 한다.

*공부할때 NHN클라우드 참고를 좀 해서 해당 내용이 들어가있습니다.*

> [!note] 프라이빗 IP 문제를 해결하는 다른 방법은? 이론적으로는 모든 장치에 글로벌 IP를 직접 할당하면 된다. 하지만 IPv4 주소가 부족해 현실적으로 불가능하다. **IPv6**가 완전히 보급되면 모든 장치에 글로벌 IP를 직접 부여할 수 있어 NAT가 필요 없어지는 방향으로 나아가고 있다.

### NAT (Network Address Translation)

- 글로벌 IP ↔ 프라이빗 IP를 **1:1로 변환**하는 방식
- 변환표(NAT 테이블)를 작성해서 관리

```
[프라이빗 IP: 192.168.1.10] ──NAT 변환──▶ [글로벌 IP: 203.0.113.1]
```

**동작 방식**

1. 기업에 할당된 글로벌 IP와 각 장치의 프라이빗 IP를 1:1로 대응하는 변환표 작성
2. 프라이빗 IP에서 인터넷 요청 시 변환표를 통해 글로벌 IP로 변환
3. 인터넷에서 응답이 오면 글로벌 IP → 프라이빗 IP로 역변환

**한계**: 글로벌 IP 수만큼만 동시 접속 가능 → 주소가 부족하면 여러 장치가 동시에 인터넷 사용 불가

### NAPT (Network Address Port Translation)

- IP 주소 변환에 **포트 번호까지 활용**해 하나의 글로벌 IP로 여러 장치가 동시 접속 가능
- 일반 가정/기업에서 실제로 사용하는 방식 (IP 마스커레이딩이라고도 부름)
- 현실에서 "NAT"라고 부르는 것들은 사실 대부분 NAPT (NAT라는 용어가 먼저 자리잡아 관성적으로 혼용됨)

```
[192.168.1.10 : 3000] ──▶ [203.0.113.1 : 51234]
[192.168.1.11 : 3000] ──▶ [203.0.113.1 : 51235]
[192.168.1.12 : 3000] ──▶ [203.0.113.1 : 51236]
```

- 동일한 글로벌 IP라도 포트 번호로 어떤 장치의 요청인지 구별 가능
- 응답이 오면 포트 번호를 보고 해당 프라이빗 IP 장치로 전달
- 포트 번호 범위: 0-65535 (0-1023은 시스템 예약, 실질 사용 가능 약 64000개)

> [!note] 포트 고갈 기기 하나가 연결을 동시에 여러 개 열기 때문에 (브라우저 탭 하나에 수십 개) 실질적으로 동시 접속 가능한 기기 수는 64000보다 훨씬 적다. 대규모 환경에서는 공인 IP를 여러 개 풀로 운영하거나, NAT Gateway를 여러 개 두고 트래픽을 분산한다. NHN Cloud NAT Gateway는 Floating IP 복수 부착을 지원하지 않음 (AWS는 가능).

> [!summary] NAT vs NAPT 비교
> 
> |구분|NAT|NAPT|
> |---|---|---|
> |변환 기준|IP 주소만|IP 주소 + 포트 번호|
> |동시 접속|글로벌 IP 수만큼|하나의 글로벌 IP로 다수 가능|
> |현재 사용|거의 없음|사실상 표준|

### SNAT와 DNAT

|구분|방향|설명|예시|
|---|---|---|---|
|SNAT|내부 → 외부|출발지(Source) IP 변환|IGW, NAT Gateway|
|DNAT|외부 → 내부|목적지(Destination) IP 변환|Floating IP, 로드밸런서|

> [!tip] IGW와 SNAT의 관계 IGW는 "문" 역할을 하면서, 통과하는 순간 SNAT 동작을 수행하는 주체이기도 하다.
> 
> - IGW = 장비/역할 명칭
> - SNAT = 그 문을 통과할 때 일어나는 동작 방식
> 
> Floating IP 할당 시 내부적으로 DNAT 규칙이 등록되어 공인 IP → 사설 IP 변환이 이루어진다. 외부에서 인스턴스로 들어오려면 Floating IP가 붙어있어야 한다.

### Stateful 동작

NAT Gateway는 **연결 상태(NAT 테이블)를 추적**하기 때문에, 내가 먼저 요청한 것에 대한 응답은 인바운드 트래픽이라도 통과시킨다.

```
✅ 내부에서 먼저 요청 → 외부 응답으로 파일 수신 (가능)
❌ 외부에서 먼저 연결 시도 (차단)
```

핵심은 **누가 먼저 연결을 시작했냐**. 파일이 내부로 들어오더라도 내가 먼저 요청한 것에 대한 응답이면 통과된다.

## 라우팅 (Routing)

인터넷은 전 세계 LAN을 연결한 것. 방대한 패킷을 처리하려면 목적지 지정뿐 아니라 **경로를 제어하는 라우팅**이 필요하다.

### 라우터의 기본 동작

- 자신이 관리하는 LAN으로 들어오는 패킷 → 수신
- 목적지를 아는 패킷 → 해당 라우터로 전달
- 나머지 → 폐기 (기본 게이트웨이가 없는 경우)

### 메트릭과 라우팅 테이블

- **메트릭**: 경로의 비용 정보 (홉 수, 회선 속도, 요금 등)
- **라우팅 테이블**: 목적지와 경유 라우터, 메트릭 정보를 관리하는 표

라우팅 테이블 덕분에 경유 라우터 수 최소화, 고장 난 라우터 우회, 최저 요금 경로 선택 등이 가능하다.

> [!tip] 리눅스에서 라우팅 테이블 확인
> 
> ```bash
> ip route show              # 라우팅 테이블 전체 확인
> ip route get <목적지 IP>   # 특정 목적지의 경로 확인
> ```

### Longest Prefix Match

목적지 IP에 여러 경로가 매칭될 경우 **가장 구체적인 경로(prefix가 긴 것)**를 선택한다.

```
목적지: 192.168.1.10

192.168.1.0/24  → /24 = 가장 구체적 → 선택
192.168.0.0/16  → /16
0.0.0.0/0       → /0  = 마지막 수단 (디폴트 라우트)
```

디폴트 라우트(0.0.0.0/0)는 아무것도 매칭되지 않을 때 마지막으로 쓰는 것.

### 정적 라우팅 vs 동적 라우팅

||정적 라우팅|동적 라우팅|
|---|---|---|
|경로 설정|관리자가 직접 수동 입력|라우터끼리 자동으로 협상|
|유연성|낮음|높음|

> [!note] 클라우드에서의 라우팅
> 
> - VPC 내부 → 플랫폼이 자동 관리 (동적에 가까움)
> - 외부 연결 → 라우팅 테이블에 수동 추가 (정적)
>     - 예) `0.0.0.0/0 → IGW` (인터넷), `10.0.0.0/8 → VPN` (온프레미스)
> 
> 온프레미스와 VPN/전용선으로 연결할 때는 BGP로 동적 라우팅도 가능.

## AS (Autonomous System)

> [!summary] AS란? **하나의 조직이 관리하는 라우터들의 집합**
> 
> 장비가 물리적으로 어디에 있든, 얼마나 넓게 퍼져 있든 상관없이 **같은 조직이 라우팅 결정권을 갖는 라우터들**이 하나의 AS를 이룬다.

### AS 번호 (ASN)

- AS마다 고유한 번호를 부여받음
- 발급 체계: **IANA → 지역 인터넷 등록기관(RIR) → 신청 조직**
    - 한국은 **APNIC**이 담당
- AS 번호를 발급받는 조건: 독립적인 라우팅 정책을 운영할 수 있는 조직

### AS를 갖는 조직의 예

- KT, SK, LG 같은 통신사업자
- AWS, NHN Cloud 같은 클라우드 사업자 (CSP)
- 대학교, 공공기관 (대규모 자체 회선 운영)
- Google, Kakao 같은 대형 인터넷 기업

### 일반 기업과 AS의 관계

일반 기업(예: 으뜸정보기술)은 AS 번호를 직접 갖지 않고, 통신사업자(예: KT)의 AS를 **경유**해서 인터넷에 접속한다.

```
[으뜸정보기술 내부망]
         ↓
  KT 라우터 (KT AS 진입)
         ↓
  KT 백본망 (KT AS 내부)
         ↓
  다른 AS (AWS, Google 등)
```

> [!tip] 아파트 비유
> 
> - 으뜸정보기술 내부망 = 아파트 세대
> - KT AS = 아파트 단지 도로망
> - 인터넷 = 외부 도로
> 
> 세대에서 외부로 나가려면 단지 도로를 경유하지만, 세대가 단지에 **소속**된 건 아니다.

### 클라우드와 AS

NHN Cloud나 AWS에서 VPC를 만들고 라우팅 테이블을 설정하는 것은 해당 CSP의 AS **내부** 작업이다. 온프레미스와 Direct Connect/VPN으로 연결할 때 BGP 설정이 필요한 이유는, 그 순간 두 AS가 경계에서 경로 정보를 교환하기 때문이다.

---

## 라우팅 프로토콜

라우터 간 경로 정보를 교환하는 프로토콜. AS 내부와 AS 간으로 나뉜다.

```
IGP (AS 내부)
├── 거리 벡터형  →  RIP
├── 링크 상태형  →  OSPF  ← 현재 주류
└── 하이브리드형 →  EIGRP (시스코 전용)

EGP (AS 간)
└── 경로 벡터형  →  BGP  ← 인터넷 표준
```

### IGP (Interior Gateway Protocol)

**같은 AS 내부** 라우터들끼리 경로 정보를 교환하는 프로토콜.

|프로토콜|방식|특징|
|---|---|---|
|RIP|거리 벡터형|가장 단순, 소규모 네트워크용|
|OSPF|링크 상태형|기업 내부망 표준, 현재 가장 많이 씀|
|EIGRP|하이브리드형|시스코 독자 프로토콜, 시스코 장비 전용|

### EGP (Exterior Gateway Protocol)

**AS 간** 경로 정보를 교환하는 프로토콜. 현재는 사실상 BGP 하나.

|프로토콜|방식|특징|
|---|---|---|
|BGP|경로 벡터형|인터넷 AS 간 라우팅의 사실상 유일한 표준|

> [!note] EGP라는 이름의 프로토콜 EGP는 AS 간 프로토콜의 **분류명**이기도 하지만, 초기에 실제로 EGP라는 이름의 프로토콜이 존재했다. 지금은 퇴역했고 BGP가 그 역할을 완전히 대체했다.

### 동작 방식 4가지

**거리 벡터형 (Distance Vector)**

- 각 라우터가 이웃 라우터에게 "나는 목적지까지 몇 홉이야"만 알려줌
- 전체 지도는 모르고 이웃의 말만 믿는 방식
- 단순하지만 느리고 대규모 네트워크에 부적합
- 대표: **RIP**

**링크 상태형 (Link State)**

- 각 라우터가 전체 네트워크 지도를 직접 가지고 있음
- 모든 라우터가 서로 상태 정보를 공유해 각자 최적 경로를 계산
- 빠르고 정확하지만 계산량이 많음
- 대표: **OSPF**

**하이브리드형 (Hybrid)**

- 거리 벡터형 + 링크 상태형 혼합
- 시스코 장비에서만 동작해 범용성이 낮음
- 대표: **EIGRP**

**경로 벡터형 (Path Vector)**

- 홉 수가 아니라 **경유하는 AS 목록**을 전달
- "목적지까지 AS1 → AS3 → AS7을 경유해야 해" 방식
- AS 간 루프 방지가 핵심 목적
- 대표: **BGP**

> [!summary] 방식별 비교
> 
> |방식|핵심 정보|규모 적합성|대표 프로토콜|
> |---|---|---|---|
> |거리 벡터형|홉 수|소규모|RIP|
> |링크 상태형|전체 토폴로지|중대규모|OSPF|
> |하이브리드형|둘 다 활용|중대규모|EIGRP|
> |경로 벡터형|AS 경유 목록|인터넷 전체|BGP|

## 기본 게이트웨이 (Default Gateway)

라우터는 자신이 관리하는 LAN으로 들어오는 패킷과 라우팅 테이블에 목적지가 있는 패킷만 처리한다. **목적지를 알 수 없는 패킷은 기본적으로 폐기**한다.

> [!note] 폐기 여부를 확인하려면? 라우팅 테이블에 경로도 없고 기본 게이트웨이도 설정되지 않은 상태에서 알 수 없는 목적지로 패킷을 보내면 라우터가 패킷을 버린다.
> 
> ```bash
> ip route show              # 라우팅 테이블 및 기본 게이트웨이 확인
> ip route get <목적지 IP>   # 해당 목적지로의 경로 확인
> # 실제 폐기 확인은 tcpdump 또는 iptables 로그 활용
> ```

### 기본 게이트웨이란?

라우팅 테이블에서 판단할 수 없는 목적지의 패킷을 **기본으로 전송할 곳**을 지정하는 개념.

```
목적지를 모르는 패킷 도착
        ↓
기본 게이트웨이가 있으면  →  지정된 라우터로 전달
기본 게이트웨이가 없으면  →  패킷 폐기
```

### LAN 내 장치의 기본 게이트웨이

LAN 내부 장치 입장에서 "모르는 목적지는 일단 라우터한테 넘긴다"고 설정해두는 것이 기본 게이트웨이다. 그래서 **LAN 내 각 장치의 기본 게이트웨이 = 라우터의 IP 주소**를 지정한다.

```
PC (192.168.1.10)
기본 게이트웨이: 192.168.1.1  ← 라우터 IP

→ 모르는 목적지 패킷은 192.168.1.1(라우터)로 전달
→ 라우터가 외부 네트워크로 연결해줌
```

### 라우터에서의 기본 게이트웨이

라우터 자신도 기본 게이트웨이를 설정할 수 있다. 자신의 라우팅 테이블로 판단할 수 없는 목적지는 상위 라우터(인터넷 경계 라우터 등)로 넘기도록 지정한다.

```
[으뜸정보기술 라우터]
  → 모르는 목적지 → KT 라우터(기본 게이트웨이)로 전달
  → KT 라우터가 인터넷으로 내보냄
```

> [!summary] 패킷 전달 흐름 전체
> 
> ```
> PC → (기본GW) → 사내 라우터 → (기본GW) → KT 라우터
>    → KT AS 내부 라우팅(IGP)
>    → 목적지 AS 경계에서 BGP(EGP)
>    → 목적지 서버
> ```
